Concrete findings and interpretation
------------------------------------
* GPS duplicate is real: USB_PD_SDA, In1.Cu, width 0.2 mm, endpoints (190.000,23.800) and (186.4125,27.3875). UUIDs d7b8e1df-0119-47f3-8b93-689739b6dd2d and d98c40c1-6bb1-410e-b18d-466cc4ef4b13 have identical geometry. Confirmed independently with KiCad pcbnew, not only the linter parser. This is a useful cleanup finding.
* Programming carrier: all 52 warnings are 45 trace.zero_length and 7 trace.duplicate. Example zero-length warning 65de023c-7980-4cea-9d50-4a26ba7cdd21 on BUF_FPGA_RGB2 is actually 0.0005 mm; the message supplies the small nonzero length, consistent with the configured 0.001 mm tolerance. Those are useful near-degenerate cleanup candidates, not proof of electrical faults.
* Module: every one of the 450 warnings is trace.minimum_width. Its actual .kicad_pro min_track_width is 0.1 mm; the linter defaults to 0.15 mm. There are 447 tracks at 0.1 mm and three at 0.125 mm. These warnings indicate a default-profile mismatch, not violations of this project's configured floor. The CLI does not automatically load project rules. Exposing the selected profile prominently would prevent this large distracting warning count.
* Reference import: 289 via.annulus warnings plus five near-zero tracks. Parsed annuli are 278 x 0.0762 mm and 11 x 0.0024 mm, below the default 0.1 mm. The 11 especially small annuli warrant checking the imported geometry/manufacturing intent; no board repair attempted.
* Tesla: 537 info findings, no warnings/errors. Largest groups: 198 via.role_missing, 91 trace.mergeable, 80 trace.width_transition, 70 pad.oblique_exit, 41 width.taper. With no intent file, missing via roles are unsurprising and represent review bookkeeping rather than discovered bad vias. The summary calls every open info finding "actionable"; "open/unreviewed" would communicate this more accurately.
* Tesla passive alignment correctly identifies R25 at y=28.8 versus R26/R27 at y=29.3 and proposes +0.5 mm on R25. These are 5.1k, 100k and 150k resistors; the suggestion is geometric, not evidence that they are functional peers or should move. The low-confidence label and caution are appropriate.
* Local shortcut output is concrete and useful: LED tester /SIG- proposes saving 1.092 mm; carrier ESP_GPIO8 saves 2.535 mm and VIN_5V saves 1.444 mm. Coordinates and affected segment UUIDs are present. I did not alter copies or run DRC on replacements, so these remain candidates, not independently validated legal routes.
* No via.overshoot, via.low_attachment or route.layer_excursion findings on these six default runs. This is a result of this sample/configuration, not evidence of detector recall.

Independent verification and successful behavior
------------------------------------------------
* Compared ALL 3,465 parsed pad centers with KiCad 10.0.6 pcbnew across the six boards. No mismatches above 0.000003 mm; counts matched on each board. See native-pad-comparison.json. This validates positions on this sample, not all pad shapes, rotations, polygons or connectivity.
* Repeating LED lint produced an identical parsed JSON report, including keys/evidence.
* Temporary ignore ledger replay worked: 8 findings became 7 actionable + 1 ignored, with review_audit status applied. No persistent engineering review decision was created in the repo.
* --fail-on warning returned exit 2 on the module and still wrote the report, as documented. Default runs returned 0 despite findings, also as documented.
* All six self-contained HTML files generated. Their embedded JSON parsed and executable JavaScript compiled with Node. Browser interaction and visual rendering were not exercised. See html-validation.json.
* Unsupported geometry is surfaced: reference board has three unsupported_geometry entries and two partial_unsupported_geometry entries instead of blanket passes.

CLI/documentation gaps and source inspection
--------------------------------------------
1. Definite catalog inconsistency: 69 rules say status=implemented but confidence=not_evaluated and caveat begins "Not implemented...". For example copper.stale_stub and mechanics.edge_clearance nevertheless emit findings on real boards. Suggested action also says "Implement with labelled positive/negative examples before enabling". That contradictory text is exposed through the public rules command and needs to be updated. README says 99 implemented checks; binary emits 101 catalog/coverage entries, reflecting the two added checks.
2. --help lists subcommands without descriptive summaries. lint --help gives no explanation for board identity persistence, output format/default destination, config lookup/loading, or what the reviews file means. README provides the essential board-ID/ledger semantics; those deserve short CLI descriptions too. The first rules invocation dumped ~1,100 lines and was truncated in the agent interface; saving it to a file was the practical workaround. A compact list/one-rule selector would help.
3. Numeric defaults such as min_trace_mm=0.15, min_annulus_mm=0.1, route.clearance_mm=0.15 and join_tolerance_mm=0.001 were easiest to discover in the report's effective config. CLI help does not show them. The README does explain init-config, but a quick-start example making profile selection and the lack of .kicad_pro import explicit would avoid the module mismatch.
4. Most checks are not evaluated without contracts: ordinary runs have 58 needs_input + 8 needs_contract; 34-35 evaluated. The terminal summary only reports "101 coverage entries", hiding this distinction. A one-line evaluated/needs-input/unsupported/budget summary would help. needs_contract is present in reports but omitted from the README's initial coverage-status explanation.
5. route.legal_shortcut is budget_exhausted on module, GPS, carrier and Tesla. The README documents 4096 windows/32 graph searches, but the report has only one status string. I inspected src/advanced.rs local_shortcuts to distinguish window cap, router-call cap and individual search exhaustion and to learn whether later cheap candidates continue (they do after the call cap; the window cap returns). Report counts/reason/coverage extent and make board-wide budgets configurable; current status alone cannot explain whether most of the board was screened. Tesla needed ~30 s despite no shortcut findings.
6. I inspected src/lib.rs Finding/Report/Coverage definitions to understand the JSON schema, lifecycle fields and coverage representation. There is no discoverable schema/help output explaining them. A schema/example report would make programmatic consumption easier.
7. I read README for contact-sheet controls and approximation limits. CLI only describes the output as a self-contained HTML sheet; no issues generating it, but UI quality was not tested here.

Failed commands and limitations of the trial
--------------------------------------------
No unexpected pcb-lint failures. The module's exit 2 with --fail-on warning was intentional. The first rules command's output was too large for the tool display; saved rules.json retains it all.

One auxiliary validation script of mine failed: it initially passed application/json script elements to Node's JavaScript compiler and received Unexpected token ':'. I corrected the harness to JSON.parse those elements and compile only executable scripts; all six then passed. This was a harness mistake, not a generated-HTML defect. KiCad's Python import/load printed property-enum assertions and repeated image-handler debug messages; all native reads completed, so these are separate KiCad runtime noise, not pcb-lint stderr.

No browser executable was available through the probed chromium/chromium-browser/google-chrome commands. No browser was installed for this trial. No native DRC, design-contract calibration, shortcut replacement validation or formal false-positive/false-negative corpus was attempted.

Recommended priorities
----------------------
Fix stale catalog metadata; expose effective fabrication profile and coverage counts in terminal output; make shortcut budget reason/counts visible; document report schema and flesh out CLI help. The demonstrated duplicate/near-zero detection, stable identities, contact-sheet generation and ledger replay are already useful for advisory review.
